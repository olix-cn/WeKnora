# 知识库成员权限：测试部署清单

> 2026-11-17。代码已挂载管理服务、路由与知识库详情页权限面板；已获授权完成测试服部署及基础上线检查。现有知识库未自动设置受限策略，业务权限验收应使用合成资料。具体主机／备份信息仅保存在私有上下文。
> 适用于受控测试验收，不等同生产安全认证或全站数据撤回。

## 已验证的部署前提

- 后端 repository／service／handler／router／container 等相关完整回归；repository／handler／router／database／config 的 race、相关 vet。
- PostgreSQL 17 独立库策略／分享／任务保护与来源索引三轮 race。
- 完整历史 SQL 至139，再140→141、空数据回退、保留来源拒绝回退；额外使用实际测试服**纯结构快照、无业务行**验证140／141。
- 固定运行基础镜像内编译（含 anydoc），动态库兼容；同一固定基础隔离启动实际后端，真实 JWT 登录后 GET／PUT 策略、管理员可读、未授权成员拒绝库详情／名单／候选／恢复状态。
- WebKit 使用生产前端构建和真实路由／service／临时 SQLite：打开面板、移除授权、确认、保存、重新打开核对；页面其余依赖为合成夹具，不将其称完整登录 E2E。
- 前端2762项（2761通过、1跳过）、类型检查、生产构建通过；构建有既有大 chunk 提示。
- 正式Swagger生成与契约全包测试、最终差异lint（0 issues）通过。验证临时容器已清除；此前按授权清理可再生成的宿主机构建缓存，不删除业务卷或保留镜像。

## 首轮测试范围与限制（验收前必须告知）

1. 在同一空间建立**合成资料与合成成员**测试继承／指定成员，不先拿真实保密资料做试验。只验当前管理员、创建者、委派管理员、编辑者、viewer及未授权成员；机器入口应拒绝受限库。
2. 迁移前消息标记 `legacy_unverified`。若成员无权读取本空间任一受限库，旧会话保守隐藏；不会删除正文，不提供业务用户自行“已核对、降密”的开关。新会话按显式单调来源检查，fork继承来源及旧数据标记。
3. 已下载、已发送字节、过去有效云签名不可收回。SSE按输出批次复查，检查与发送间仍有调度窗口，不承诺事务级零字节撤回。
4. 不是全站信息流控制。长期记忆、沙箱／外部导出和迁移前缺失来源无法证明完整血缘；正式保密上线前需独立治理。第一轮验收应禁用这些派生使用场景，不能以测试通过宣称其已经支持撤回。
5. 受限源库跨库复制／移动暂不支持；异常转存不会自动解锁。状态与 failed恢复提供管理员 API，active／崩溃只能获维护授权后离线核对，无 force。
6. 临时证据可能含引用／工具结果。遵循原会话的业务敏感数据访问、备份及软删除保留规则；索引事务成功即压缩证据。显式回填可压缩长期未读的证据，但不得用TTL直接删证据而丢来源。会话软删不等于物理销毁；生产账号清除／备份销毁和自动保留期作业仍需专门评审，首轮测试仅合成数据。
7. 部署工作树与开发树含累计发布补丁及新上游差异，应整体核对，不得视为同一提交。已核对69个原基线发布修改：37个逐字相同，28个三方合并结果已被开发树包含，4个冲突块人工确认是开发树保留并新增内容，不应倒退覆盖。
8. 新开发树含 BrowserSkill 0.4.1相关上游，而固定基础带0.3.1；本次权限验收不启用浏览器扩展／桌面联动。不能悄悄安装或升级配套依赖；如需验收该入口须单独批准并核对资源。

## 打包与上线（需要明确部署授权）

1. 重新确认运行镜像、当前schema版本／dirty、工作树差异、空间与进行中转存任务；建立必要备份与回退坐标。不把本文快照当当前运行事实。
2. 复用固定编译输出、缓存与构建锁，默认 `-p 2`。**不能用宿主机二进制直接打包**：本次发现宿主机 glibc／libstdc++ 版本高于固定基础；须在固定基础内编译并检查 `ldd` 无缺失版本。
3. app从固定原版 runtime镜像构建，不得 `FROM` 当前补丁镜像。完整复制新程序、`config/`、`migrations/`、实际所需 `scripts/`、`dataset/samples/`和适用许可资源；前端从固定ui基础复制完整dist。保留运行所用外部挂载与本机配置，不把密钥或业务文件复制入镜像。
4. 校验构建输入与输出hash、源代码在构建期间未变；Swagger变动也会嵌入程序，最终生成文档后须重建。不要直接运行旧的一键发布参考脚本。
5. 在原测试服 Compose下显式执行140／141迁移；失败停止、核对dirty，不自动force。原139默认继承，不会自动给现有库设置受限。
6. 只切换app／frontend，保留原PostgreSQL／Redis／Qdrant／DocReader配置和业务卷；不要启动备用开发Compose替代测试服。先health与继承回归，再用合成资料做权限验收。
7. 验收关键动作：并发保存409、移除创建者、委派管理撤销、viewer上限、离开再加入不复活、手拼ID／文件／引用／问答／历史／续流／分享／API-key拒绝、转存中策略冲突及恢复坐标核对。

## 回退

- 首选回切上一已验收app／frontend镜像，**保留新增表和来源数据**。旧程序不认识受限策略，存在受限资料时直接回旧版会重新开放访问：必须先维护隔离／停对外访问、完成受众核对后才允许回切，不能只追求health恢复。
- 141 down遇来源或临时证据拒绝；140 down遇restricted、显式授权或未恢复转存标记拒绝。不能删表／清标记／清来源强行回退。
- 不将整库备份直接覆盖上线后的新业务数据。需数据恢复时另行评审联合恢复点与停写窗口。

## 管理 API

全部位于 `/api/v1`、只接受真实用户JWT，并重新检查数据库中的当前角色；API key不能借owner身份管理。

| 方法 | 路径 | 权限 |
|---|---|---|
| GET / PUT | `/knowledge-bases/:id/member-access` | 当前知识库admin |
| GET | `/knowledge-bases/:id/member-access/candidates?q=&page=1&page_size=20` | 当前知识库admin |
| GET | `/knowledge-base-transfers?limit=100` | 当前空间owner/admin，最多100条最早未解决尝试 |
| POST | `/knowledge-base-transfers/recover` | 当前空间owner/admin，仅failed，人工停止与核对确认 |

PUT必须提供 `mode`、`expected_version`、完整 `members`。409须重新加载，禁止无版本盲覆盖。恢复流程见 [转存异常恢复](knowledge-base-transfer-recovery.md)。

# 知识库转存异常恢复

> 未部署；开发树管理接口已注册，不是现有部署的操作指令。不要直接对业务库清表或按时间删除标记。

## 标记含义

每次执行独立记录 `knowledge_base_transfer_fences`，绑定空间、源库、目标库和任务。

- `active`：执行中，或者进程中断／panic／标记更新失败而无法证明已结束。
- `failed`：执行回调已返回错误；文件、向量库或数据库仍可能有部分提交，不表示已回滚。
- 成功只删除本次尝试的标记。同任务较早失败、未知尝试不被成功重试自动清除。
- 有标记时禁止变更参与库的权限；没有 TTL 自动解锁。

## 可用的恢复原语

`GET /api/v1/knowledge-base-transfers?limit=100`提供当前空间owner/admin只读状态，最多100条最早未解决尝试，不含业务载荷。处理后可重新查询；不宣称是完整队列控制台。

`POST /api/v1/knowledge-base-transfers/recover`（`KnowledgeBaseMemberService.RecoverFailedTransfer`）：

1. 当前真实人类成员必须在该空间为 owner/admin；API key、系统管理员身份或库级委派 admin 不能替代当前空间角色。
2. 必须精确匹配 fence、task、source、target 和当前空间。
3. 仅允许 `failed`，且同任务没有任何 active 尝试。
4. 管理员必须确认 `worker_stopped=true`、`outcome_reconciled=true`，并填写不含密钥或业务正文的核对说明。
5. 审计 `kb.transfer_recovered` 与删除该次标记同事务；审计失败保留标记。

这是管理员的核对确认协议，不是服务端自动证明外部系统已回滚，也不会自动重放任务。

## 核对流程

1. 确认目标任务、队列重试与所有实例的执行状态。暂停／取消该任务的自动重试并取得维护授权；不要停止无关业务服务。
2. 查明源和目标数据库记录、文件、向量索引、图谱及任务检查点是否一致。对部分成功保留逐项结果，不按文件名猜结果。
3. 选择修复前向状态、显式回滚或承认部分结果；涉及数据写入先备份、获授权，并完成独立验证。
4. 确认相关 worker 已停止且不会再次执行，使用精确坐标确认恢复。恢复不修改资料或权限；之后再次读取当前策略再决定下一步。
5. 重复恢复返回未找到，不把重复点击算成新的成功修复。

## active／崩溃标记

在线恢复原语**拒绝** active，即使管理员勾选确认、即使标记很旧也不删除。
需获维护授权后核对所有执行实例与队列，确认进程已终止、外部结果已处理，再通过经评审的离线恢复操作处理精确标记并留审计。
目前不提供通用 force 接口或自动 SQL，避免误解锁仍在运行的任务。

## 已验证

- 正常失败进入 failed；成功兄弟尝试不删除它。
- 普通成员伪造 owner、机器 key、缺确认、错误任务坐标均拒绝。
- active、同任务 active 兄弟尝试均拒绝。
- 审计失败整笔回滚，标记不丢失。
- PostgreSQL 隔离实库三轮 race 验证恢复和审计，与迁移／策略／分享竞争测试一起通过。

## 发布门槛

状态与failed恢复API已挂载，尚未上线。队列停重试与结果核对由获维护授权的操作者执行，不提供一键自动操作；active离线恢复需另行评审，不宣传业务人员自行“一键恢复”。

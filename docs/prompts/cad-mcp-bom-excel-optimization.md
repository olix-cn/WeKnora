# CAD Assistant MCP：BOM 读取与 Excel 导出优化提示词

以下代码块可整体复制给 CAD Assistant MCP 服务端的开发 AI。
这是待实现的优化要求，不代表功能已经开发、测试或部署。

```text
请优化 CAD Assistant MCP 的 BOM 读取与 Excel 导出链路。重点不是加快磁盘读取，而是让 Agent 一次取得真实表头及完整结构化数据，避免因通知膨胀、结果截断和字段试探产生多轮模型调用，并避免每次临时生成一大段 Excel 脚本。

一、已验证的背景

一次真实的“读取 BOM 合并为完整 Excel”请求：
- 总耗时 191.14 秒。
- 主 Agent 19 次模型调用累计 151.62 秒，约占 79.3%。
- 一次询问导出列范围等待 32.65 秒。
- 主链路 CAD 数据读取合计只有约 1.35 秒。
- Excel 脚本实际执行、保存和重新加载检查约 0.60 秒；生成该脚本的模型调用却耗时 35.19 秒。
- 一个并行表头调查子任务持续约 78.95 秒，仍无法补齐两列组合表头。该时间与主任务重叠，不能再次加到端到端总耗时上。

读取过程的具体问题：
1. drawing_read_files 开启 include_proxy_graphics=true 后，三文件原文约 103.75 KB，模型可见结果被截断。
2. drawing_bom_extract 首次目录提取约 66.80 KB，大量体积来自原始诊断通知；后续单文件读取仍约 21.78 / 37.44 / 36.50 KB。
3. WeKnora 工具通道对过大 output 约在 24000 字符处截取头尾，可能切入 JSON 字符串，业务数据或表头证据随之缺失。
4. limit/offset 主要控制 BOM 行或普通块定义/引用，不限制诊断通知，也不能定向取回被截掉的代理表头文本。调小 limit 并未解决问题。
5. Agent 先提取三列，再尝试增加“单重”等列，工具因真实显示表头缺失或歧义而拒绝；随后重新读取两张图的六列数据。
6. 返回中同时出现有效行、空白单元格问题和某文件无明细表状态；传输 success=true 不代表业务数据完整。
7. 最终只得到两张装配图的 12 行、六列数据，另两列组合表头及内容未确认。Excel 正确标注为“已提取数据版”，未达成全部原表列完整导出。
8. prompt 从约 2.19 万增长到 6.80 万 tokens，模型反复阅读结果并手动把数据写入 Python。

重命名接口已实现告警摘要化，但不能假设 BOM 和通用图纸读取接口也已经具备相同能力。请以仓库当前实现为准。

二、工作边界

1. 先阅读仓库说明和 AGENTS.md，检查 Git 状态，不覆盖已有改动。
2. 定位 drawing_read_files、drawing_bom_extract、保存后 Mechanical 显示表解析、通知收集、分页、文件导出及 MCP 序列化代码。
3. 先给出基于实际代码的缺口分析和最小实施方案，再开发与测试。
4. 不修改 WeKnora 服务端、客户端截断上限、模型配置或 Agent 权限。
5. 不安装依赖、不重启生产服务，不用真实用户文件执行写入测试。
6. 保持向后兼容。优先复用现有能力；必要的新参数或工具必须职责清晰，不堆叠多个相近工具。
7. 不为了提速隐藏阻塞问题、猜表头、补数据、跳过文件有效性或越权读取。
8. 保存文件显示表与原生 Mechanical BOM 是不同数据源。不得默默切换，不得将图面文字读取包装成原生 ACMBOM 数据库读取。

三、先提供实际表头与可提取能力，而不是让模型试列名

为 BOM 提取提供紧凑的表结构发现能力，可采用现有工具的模式参数或职责独立的只读接口。

至少返回：
- 每文件的读取状态、数据来源、解析器版本或必要来源标识。
- 已发现表的稳定 table_id、布局、句柄和行数。
- 按实际显示顺序排列的全部表头，含原文、稳定 column_id 和列位置。
- 多级/组合表头的父子关系、合并范围及可证明的坐标信息。
- 已确认表头、空表头、未解码表头、歧义表头的不同状态。
- 每列是否可提取、是否需要额外证据，以及明确原因。
- 是否存在其他表/页、是否完整枚举及下一页参数。

对于重量等组合表头：
- 保留原始层级或表头路径，不直接合并成未经证实的“单重”“总重”。
- 仅网格坐标可确认而文字不可确认时，如实返回位置和 unknown/unresolved 状态。
- 用户可通过稳定 column_id 选择列，不能靠猜测中文名称才能访问数据。
- 明确区分 schema 完整、所有物理列已返回、所有列语义已识别，不能只用一个 complete 混为一谈。

用户已经明确要求“全部原表列”时，应有清晰的全列选择能力：
- 不改变现有 columns 默认值的含义。
- 设计显式的全列选择参数/模式，并处理不同文件的异构表头。
- 不把所有 columns=null 或 omitted 的旧调用突然改成全列。
- 若全列导出仍无法可靠读取某列，返回明确缺口，不能用六列投影冒充完整原表。

四、将业务摘要、诊断和原始图形证据分离

默认摘要应优先保留：
- 实际表头、行列数据或完整性明确的数据分页。
- 数据源、文件/表标识、数量、覆盖范围和完整性状态。
- 必须处理的阻塞问题、歧义以及缺失证据。
- 分类后的非阻塞告警数量、影响说明和详情获取方法。

禁止默认夹带：
- 数十 KB 的全部解析器通知。
- 与目标 BOM 无关的块、实体、所有代理图形线段或重复文件元数据。
- 每行反复复制整份解析证据、长路径和原始对象；可用稳定引用关联，保持必要溯源。

要求：
1. 将经现有校验证明不影响所选读取范围的通知聚合为稳定 code/scope、数量和影响。
2. 不把 blocks_attribute_read=false 自动解释成“所有 BOM 单元格都完整”。BOM 显示表读取完整性须独立判断。
3. 未分类、未知影响和阻塞通知不得降级为无害信息；同类不同影响应分别表达。
4. 将原始通知、完整图形证据放到显式 full/diagnostics 或专门详情读取中。
5. text 与 structuredContent 若需同时保留，应表达同一份紧凑结果，不能一份摘要、一份全部通知。
6. 不对最终 JSON 硬截断；保持完整可解析，超出预算时使用结构化分页/数据制品或明确受限状态。
7. 对三文件、12 行、八列和大量非阻塞通知的合成样本，争取默认结果在 8 KiB 左右，至少保证单页模型可见结果低于 16 KiB。不能通过漏行、漏列或隐藏问题实现；必要时正常分页。

五、为表格和证据提供真正可用的分页

不要继续复用只控制普通块定义的 limit 来假装代理表头可分页。

按实际需求支持：
- 文件选择分页。
- 表选择和 schema/表头读取。
- BOM 行分页与显式列投影。
- 单表原始表头文字、指定列/单元格的定向证据读取。
- 原始诊断通知分页。

返回明确的 total、offset/limit 或 cursor、has_more、next_offset/next_cursor、complete_for_requested_scope。

分页应绑定稳定的读取快照或等效文件状态：
- 不把不同修改版本的图纸结果拼接在一起。
- 后续文件变化时拒绝过期快照或明确要求重新读取。
- 快照/结果引用要有用户/会话授权、有效期和容量边界，不能凭猜到标识越权读取。
- 不因回读、切换摘要或翻页自动刷新快照有效期。
- 详情读取不产生 CAD 写入，不为读取而重开 CAD。

六、精确定义空白单元格和部分成功

请区分以下状态：
- 已可靠识别单元格边界且为空白。
- 未检出显示文字，但不能证明实际为空。
- 无法解码、读取缺失、歧义、列不支持。
- 文件无已保存明细表。
- 原生数据库未读取。

约定明确的 value/state/issue 语义：
- 空白不自动变成 0、空字符串或“无”，尤其不能编造材料和数量。
- 只有足够证据证明为空时，才将其作为合法空白；否则保持 unknown/incomplete。
- 一个文件无明细表不应抹掉其他文件的有效行，但批次必须显式报告部分成功和遗漏文件。
- 返回完整行数、各文件状态、缺失列/单元格统计和可执行的补查方式。
- 批次 complete、某列 complete、某文件成功分别表达，不以 MCP 传输成功替代业务完整性。

七、结构化数据直接交付导出端，避免模型手抄

请核实现有 output_path 功能到底导出什么，不要假设 drawing_read_files 的引用/属性报表就是 BOM 导出。

优先选取符合现有架构的一条最小可靠路径：
A. MCP 直接将已经解析的 BOM 数据写成 Excel。
B. MCP 返回受控的数据制品/结果引用，由既有导出工具消费。
C. 返回稳定 JSON/CSV 数据文件，使用固定模板导出。

无论采用哪条路径：
- 模型只选择范围、格式和展示参数，不重新逐行抄写真实数据。
- 不将用户数据塞进 Python 源码、shell 命令或表达式执行；数据和程序分离。
- 不要求每次由模型生成样式代码；使用可复用的导出函数/模板。
- 不把工作站 Windows 路径当成 WeKnora Linux 沙箱路径，也不假设两端共享文件系统。
- 工件交付使用客户端实际支持的协议；不能只返回工作站本地路径却宣称已提供可下载附件。
- 如果客户端协议没有适用的文件交付方式，明确提出缺口，不发明 resource URL 或 sandbox URL。
- 文件名/路径需规范化，限制在授权输出目录，防止路径穿越、静默覆盖和任意文件读取。
- 导出含用户数据的文本单元格时防止 Excel 公式注入；真实公式只能由受信模板明确创建，不能默认把 =、+、-、@ 开头的来源文本解释为公式。
- 保留以零开头的图号、精度、单位及文本类型，不擅自转换成数值或日期。

八、Excel 内容与完整性

导出结果至少包含：
- 来源关联清晰的 BOM 明细。
- 文件/表的读取状态和遗漏说明。
- 数据源与验证范围，必要的未解决问题。

针对多个文件：
- 异构表头可按来源分表，或使用有明确映射的联合列；不要因同名就强行合并不同语义列。
- 多级表头保留层级或可逆的表头路径。
- 默认按来源逐行合并，不自动跨层级去重、汇总或做装配数量乘算。
- 用户要求汇总时，必须明确分组键、数量语义和装配层级，不能把子总成与其零件重复计数。
- 未完成全部列时，文件名/说明与返回状态明确标为部分结果，不宣称“完整 BOM”。

导出后重新打开验证：
- 行数、列数、表头、来源状态。
- 导出值与本次结构化源结果逐单元格一致，合法空白和 unknown 状态不丢失。
- 图号文本、数量、中文、特殊字符、公式注入防护。
- 未出现无意的公式或错误单元格。

验证导出与源结果一致，不代表独立验证了源 CAD 文件或原生 BOM 数据库。输出中保留这条边界。

九、工具描述与 Agent 决策所需信息

更新真实暴露的 description/input_schema：
- BOM 任务优先使用 BOM schema/提取能力，通用原始图纸读取不是固定前置步骤。
- 明确全列读取、投影、分页、来源类型、空白语义和完整性字段。
- 明确 include_proxy_graphics=true 是原始证据读取，不是所有 BOM 导出的必选项。
- 明确遇到截断时可采用哪种真实支持的定向读取，避免重复大结果或无效子任务。
- 明确导出路径、工件归属和下载方式。
- 结果仅返回数据，不夹带要求客户端跳过授权、安全规则或强制执行工具的指令。

十、性能指标与测试

记录不包含原始用户数据的阶段指标：
- 文件枚举、解析、表头识别、单元格提取、快照存取。
- 诊断构造、JSON 序列化、原始/返回字节数和字符数。
- Excel 写入、重新加载校验、制品交付。

测试使用 mock、临时目录和合成数据，至少包括：
1. 两个各六行的显示表，加一个无明细表的文件；批次状态、12 行数据和来源准确。
2. 多级组合表头、未知表头、重复/歧义列名，不猜测语义。
3. 合法空白、未检出文字、解码失败、缺失字段分别保持状态。
4. 数百条非阻塞通知与少量阻塞问题混合，摘要紧凑且关键问题不丢失。
5. 表头/行/证据/诊断分页不漏项、不重复，文件变化后不混合版本。
6. 回读结果不重新解析；检查解析器调用次数。缓存有失效、授权与容量限制。
7. 所有文件完整读取时全列导出；有缺失时明确部分结果，不能误报完整。
8. Excel 与结构化数据逐单元格一致，含中文、前导零、大整数、空白和公式样式文本。
9. 输出路径穿越、覆盖、未授权结果引用、过期结果访问被正确处理。
10. text 与 structuredContent 兼容性，旧参数/默认列选择行为不变。
11. 原生 Mechanical BOM 与保存后显示表不能混淆；测试不启动生产 CAD，不写真实图纸。

十一、交付标准

提交：
- 实际缺口分析、改动文件及兼容性说明。
- schema、完整数据页、部分成功、诊断详情和导出结果示例。
- 优化前后字节数、字符数、解析次数、导出/验证耗时。
- 测试命令与结果，仍不支持的表头或原生数据类型。

验收重点：
一次明确的表结构发现后即可可靠提取，不靠模型猜列名；
默认诊断不再挤掉表头和数据；
定向补查可取回缺失证据，不只是重复相同大结果；
Excel 由结构化数据和固定模板生成，不由模型逐行手抄；
完整性、来源与验证边界可被客户端判断，不能通过隐藏问题换取速度。

不要承诺固定减少多少模型轮次或秒数。MCP 服务端先验证协议、结果体积、数据正确性及调用行为，再由客户端新会话复测端到端收益。
```

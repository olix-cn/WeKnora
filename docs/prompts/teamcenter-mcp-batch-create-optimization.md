# Teamcenter MCP：批量创建 Item 优化要求

> 状态：待评审、待实现。本文可直接交给 Teamcenter MCP 服务端开发者或开发 AI。
> 目标：减少批量任务的串行模型往返，不以绕过确认、并发写入或盲目重试换取速度。

## 1. 问题与已验证事实

一次“自动分配 ID、在 Home 创建 10 个 Item”的真实请求：

| 项目 | 实测耗时 |
| --- | ---: |
| 后台任务总耗时 | 约 584.97 秒 |
| 12 个逻辑模型轮次，含一次重试 | 累计约 528.70 秒 |
| 一次用户确认等待 | 约 31.30 秒 |
| 10 次创建工具执行 | 合计约 21.37 秒 |

当前执行方式是“模型决定创建一个 → MCP 创建 → 模型决定下一个”，已知清单被拆成十次模型决策。部分模型请求出现约 101 秒等待，一次触发本地 120 秒无输出超时。

另外已通过合成测试验证：同一模型／网关能在一轮返回 10 个完整的虚拟工具调用；约 3 万 tokens 的合成输入也没有必然触发百秒等待。因此：

- 单轮只能返回一个调用不是协议硬限制。
- 将确定性的创建循环放进 MCP，可以减少暴露于模型长尾的次数。
- 批量工具不能消除剩余单次模型请求的网关／上游长尾，不承诺固定总时长。
- 上述 21.37 秒是工具包装耗时，不是已经核实的 Teamcenter 原生事务耗时。

## 2. 实现边界

开始实现前：

1. 阅读 MCP 仓库说明、适用的 `AGENTS.md` 和 Git 状态，保留已有改动。
2. 查清 `tc_create_item` 的真实实现、连接复用、权限校验、属性类型解析、Home 归档、错误及超时语义。
3. 查清 Teamcenter 当前版本的批量创建能力和部分错误契约，不凭接口名称假定原子性。
4. 先提出最小方案，再实现；本文的工具名和字段名是建议，须与现有风格统一。

本轮不默认授权：

- 修改 WeKnora 引擎、模型配置、工具权限、超时或输出截断上限；
- 安装依赖、重启或部署服务、迁移在线数据库；
- 在真实 Teamcenter 创建测试物料、修改已有对象或删除对象回滚。

保留 `tc_create_item` 的现有契约，新增独立批量入口。第一版优先顺序执行，不默认并发写入。

## 3. 目标流程

工具已发现、参数明确时，期望流程为：

```text
模型整理完整清单及公共属性
  → 一次用户确认
  → 一次批量 MCP 调用
  → MCP 顺序执行并保存逐项结果
  → 返回紧凑汇总
  → 模型总结
```

参考目标：由原样本 12 个逻辑模型轮次，减少到约 3 轮；工具首次发现、参数补充和异步状态查询另计，不为满足轮次数字跳过必要步骤。

如需类型／属性候选查询，在写入前一次性补齐公共信息，避免每项重复发现工具、连接检查或元数据查询。

## 4. 建议工具：`tc_create_items`

### 4.1 输入示例

```json
{
  "items": [
    {"client_ref": "row-1", "name": "批量测试1"},
    {"client_ref": "row-2", "name": "批量测试2"},
    {"client_ref": "row-3", "name": "批量测试3"}
  ],
  "defaults": {
    "type": "Item"
  },
  "confirm": true,
  "idempotency_key": "stable-key-for-this-confirmed-batch"
}
```

说明：

- 省略容器时沿用 `tc_create_item` 当前用户 Home 语义；不能接受客户端任意用户名来切换 Home。
- 允许指定已有工具支持的 `containerUid`，但必须重新检查访问与写入权限。
- `client_ref` 是批内稳定且唯一的关联键，不是物料 ID，不提交为任意业务属性。
- 单项可按明确规则覆盖公共属性；未知字段拒绝，不能静默忽略。
- ID、版本号等字段沿用现有单项工具名称及自动分配语义，不在重构中悄悄改变。
- `confirm:true` 只是调用参数，不等于已经证明用户确认；继续执行现有平台审批与服务端写权限检查。

### 4.2 首版限制

- 建议批量上限先设为 10，限制在 schema 和运行时同时执行，后续实测再扩大。
- `items` 非空，明确列出全部对象，不把“1–10”字符串交给服务端自由展开。
- 公共／单项属性只支持现有创建能力；不夹带发布、流程、上传、BOM 修改等副作用。
- 不引入通用 `continue_on_error` 开关，首版采用固定的失败／未知状态停批规则。
- 复用已有业务实现，不把模型生成的脚本作为批量执行器。

## 5. 写入前预检和确认范围

在任何写入之前，对整批执行无副作用校验：

- 数量、名称、字段长度、批内 `client_ref` 唯一性；
- 公共参数与单项覆盖后的最终参数；
- 类型内部名、属性名、值类型及容器合法性；
- 显式指定的物料 ID 是否在批内冲突；
- 当前认证身份和可验证的创建／容器权限。

预检不等于 Teamcenter 提交保证：权限、对象状态和 ID 可在预检后变化，提交时仍须检查。

用户确认应展示全部名称、类型、公共属性及例外项、目标容器、ID／版本分配方式和失败停批规则。确认后修改清单或有效参数，必须重新确认。

如果现有框架不能可靠绑定确认范围，可增加无副作用的 prepare 模式或独立准备工具：返回 `plan_id`、有效参数摘要、过期时间及服务端计划指纹。执行必须绑定当前身份、原计划与确认范围；不能只比较客户端提交的 hash。若已有审批机制足够，不为批量工具强制新增一套重复确认流程。

## 6. 持久化幂等与逐项执行

### 6.1 批次预约

开始写入前，持久化批次预约、规范化有效参数指纹、身份范围和逐项记录。

- 幂等键必须按认证主体、服务／连接范围隔离，不是全局公开查询口令。
- 相同键、相同有效参数：返回已有批次／进度，不重复执行。
- 相同键、不同有效参数：返回明确冲突，不覆盖旧批次。
- 两个同时到达的相同请求只允许一个取得执行权。
- 键过期／记录清理后不能将旧键悄悄作为新批次执行；应明确拒绝或要求新的已确认操作。
- 不能只用进程内 map；持久化方案须适配 MCP 服务现有存储与部署形态。

### 6.2 执行规则

对每项按输入顺序执行：

```text
pending → running → succeeded
                  → failed
                  → unknown
```

每项成功后立即保存已分配的 Item ID、Revision ID、对象 UID、容器结果及可用证据，再处理下一项。

- `failed`：有明确证据证明该项没有完成预期操作。停止后续，保留已成功项。
- `unknown`：请求可能已提交但响应丢失、进程中断或部分步骤无法核实。停止后续，不能直接重试创建。
- `not_attempted`：因停批而尚未提交的后续项，不标失败或成功。
- 若 Item 已创建但首版本／归档等后续步骤失败，保留已创建对象身份，明确部分副作用；不能把它作为“无写入失败”自动重试。

不自动删除已成功对象进行“补偿回滚”。跨项全有或全无仅在底层真正支持且经过验证后才能承诺。

### 6.3 崩溃与未知提交状态

重点处理“Teamcenter 已创建，但 MCP 还未来得及保存成功结果”的窗口：

- 如下游原生支持幂等标识，核实语义后优先使用。
- 否则评估经过批准的唯一关联标识及核对路径，不擅自向业务对象增加属性。
- 自动分配 ID 时，不能按同名检索到一个对象就断言本次成功；名称通常不足以唯一归属。
- 重启时遗留 `running` 项进入待核对状态，不直接重新执行。
- 无法可靠核对时返回 `unknown`，需要人工确认；不宣称 exactly-once。

续办仅针对经核对可安全执行的项，保留原批次与逐项关联。首版可以只开放状态查询／人工处置，不必为了闭环自动重试未知项。

## 7. 紧凑返回与按需详情

### 7.1 结果示例

```json
{
  "batch_id": "batch-example",
  "status": "completed",
  "requested": 3,
  "succeeded": 3,
  "failed": 0,
  "unknown": 0,
  "not_attempted": 0,
  "results": [
    {"client_ref": "row-1", "status": "succeeded", "name": "批量测试1", "item_id": "EXAMPLE-001", "revision_id": "A", "location": "Home"},
    {"client_ref": "row-2", "status": "succeeded", "name": "批量测试2", "item_id": "EXAMPLE-002", "revision_id": "A", "location": "Home"},
    {"client_ref": "row-3", "status": "succeeded", "name": "批量测试3", "item_id": "EXAMPLE-003", "revision_id": "A", "location": "Home"}
  ],
  "duration_ms": 21000,
  "details_available": true
}
```

以上 ID 与耗时只是示意。实际字段值必须来自真实结果，不凭输入参数推断已归档成功。

要求：

- 批次状态区分 `running`、`completed`、`partial`、`failed`、`needs_reconciliation` 等，语义写入契约。
- `completed` 只用于全部完成且无未知状态；传输成功不等于批次业务成功。
- 每项至少包含关联键、状态、成功对象身份或错误分类；未知／部分副作用必须显式报告。
- 默认不返回完整 Item／Form／Revision 属性树、重复长说明或堆栈。
- 全量告警按类型／影响聚合，阻塞信息不隐藏；详情按权限查询。
- 保持合法、完整 JSON，不依赖客户端头尾硬截断；建议 10 项 summary 以 8 KB 为初始体积预算，超预算必须解释并优化，不能删除关键状态。
- 若同时提供文本和 `structuredContent`，两者状态与计数一致，避免生成相互矛盾的摘要。

## 8. 超时、断线与进度查询

至少提供受权限保护的 `tc_get_create_items_batch(batch_id)` 或等价查询方式。

- 返回现有状态，不因查询再次提交创建；批次 ID 不代替鉴权。
- 同一批次不能被两个执行器同时续办。
- 交付前明确客户端断线语义：停止调度后续项，或由持久化任务继续处理。不得依赖会被请求销毁的临时线程／连接而声称后台可靠继续。
- 断线不会撤销已经提交的 Teamcenter 写入；取消也只能停止尚未提交项，正在提交项可能需要核对。
- 若同步执行可能超出实际 MCP／网关预算，采用“持久化预约 → 返回 batch_id → 独立 worker 执行 → 查询结果”，而不是无限增加超时。
- 如果首版采用同步方式，必须证明中断后能保存部分进度并通过查询说明状态；不能声称具备尚未实现的断线继续能力。

优先复用健康连接、一次解析公共元数据；首次连接／登录慢应单独计时。连接失效重建不能导致已经提交的业务创建被自动重放。

## 9. 工具发现与 Agent 使用规则

工具名称、描述与搜索关键词应覆盖“批量创建、多个 Item、多个物料、自动编号、Home”。

建议助手规则：

> 用户要求创建多个独立 Item 时，优先使用批量工具。一次补齐必要参数并展示完整清单供确认；确认后提交一个稳定幂等键对应的批次，不再逐项调用单对象工具。执行超时先查询批次状态，不能更换幂等键整批重试。对失败、未知和未执行项分别说明；不能把部分成功称为全部完成。

注意：

- `tc_connection_status` 的现有首次检查规则保持，不为提速绕过配置／认证检查。
- 只在完整范围已确认后执行批量写入；参数不完整或依赖前项结果时先补齐。
- 没有批量工具时仍允许原单项能力，不伪造工具名或通过 shell 绕过。
- 刷新 MCP 工具目录和助手规则属于上线步骤，需要单独授权，不由本文自动执行。

## 10. 可观测性与性能验收

建议记录无密钥的结构化指标：

- batch_id、逻辑项关联键、请求／执行器关联 ID；
- 连接获取／重建、元数据解析、预检、幂等预约、每项提交、结果持久化及总耗时；
- 重放命中、键冲突、部分成功、unknown 和未执行计数；
- 默认返回体积、工具调用数量及模型逻辑轮次。

不得记录密码、Token、完整请求头或不必要的用户属性；业务对象身份按原审计与访问策略保护。

性能比较使用相同测试条件、多次采样，分别报告：

1. 工具发现、模型时间、用户等待、MCP 执行、结果总结；
2. 冷连接与热连接；
3. 成功、失败及恢复路径；
4. 中位数与尾部样本，不只展示最快一次。

目标是显著减少模型往返，不强求 Teamcenter 原生执行提速。若底层支持原生批量请求，另行比较，不能把减少网络次数等同于事务安全。

## 11. 必须覆盖的验收用例

| 编号 | 用例 | 预期 |
| --- | --- | --- |
| T1 | 10 项合法请求 | 顺序执行，一份完整汇总，无逐项模型决策 |
| T2 | 0 项／超过上限／字段非法／重复 client_ref | 写入前拒绝，零业务副作用 |
| T3 | 公共参数与单项覆盖 | 有效参数符合明确优先级，确认范围一致 |
| T4 | 相同键相同参数重复提交 | 返回原批次，不重复创建 |
| T5 | 相同键不同有效参数 | 冲突，不修改原批次 |
| T6 | 同键并发提交 | 只有一个执行者取得写入权 |
| T7 | 第 4 项明确失败 | 前 3 项保留，第 4 项失败，后 6 项未执行 |
| T8 | 第 4 项提交后响应丢失 | 标 unknown 并停批，不自动重试创建 |
| T9 | Item 成功、首版本／归档失败 | 报告已发生副作用和对象身份，不伪装无写入 |
| T10 | 提交前后及持久化前后崩溃 | 重启后可查询，未知状态不被误当待执行 |
| T11 | 跨用户／空间／连接查询或续办 | 按身份范围拒绝，不泄露批次信息 |
| T12 | 权限撤销、容器失效、计划过期／改参 | 提交前重新校验，不绕过确认 |
| T13 | 客户端断线／取消 | 行为符合已声明契约，可查部分结果，无整批盲重试 |
| T14 | 全部成功／部分成功／未知结果 | 状态、计数、文本及结构化结果一致 |
| T15 | 返回体与诊断 | 合法 JSON、完整关键状态，无密钥和默认长堆栈 |
| T16 | 原单项工具回归 | 输入、权限、Home、编号及错误行为兼容 |

先用 mock／故障注入验证；真实写入测试仅在用户批准的隔离 Teamcenter 环境执行，使用明确测试清单，清理也需授权。

## 12. 分阶段交付

### 第一阶段：最小可靠批量

- 新增有上限的 `tc_create_items`，复用现有创建能力，内部顺序执行。
- 完成整批预检、持久化幂等、逐项状态、失败／unknown 停批及结果查询。
- 明确同步中断语义；在当前等待预算内验证 10 项场景。
- 完成紧凑结果、发现描述、使用规则和故障注入测试。

### 第二阶段：按实测需要扩展

- 可靠持久化 worker、进度和取消／人工核对后的受控续办。
- 经验证的 Teamcenter 原生批量接口、连接与元数据缓存优化。
- 上限调整、详情分页及更大批次；不默认开启并发写入。

交付时列出改动、测试、实测数据、未完成能力、部署与回退要求。不要仅以“加了一个循环”或“成功返回一次”宣称可靠批处理完成。
